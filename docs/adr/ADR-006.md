# ADR-006: Redis + BullMQ para processamento assíncrono

## Status
Aceito

## Contexto
Vários processos do produto não podem bloquear a requisição HTTP síncrona: envio de mensagem, importação de leads, processamento de gravação de chamada, geração de relatório pesado, notificações, consumo de webhooks (ver [../03-architecture/architecture.md](../03-architecture/architecture.md) seção 6). É preciso um mecanismo de fila confiável, com retry e observabilidade.

## Problema
Qual solução de fila/processamento assíncrono adotar, equilibrando simplicidade operacional (já se usa Redis para outras finalidades, como pub/sub de WebSocket e cache) e recursos necessários (retry, backoff, dead-letter).

## Opções consideradas
1. **Redis + BullMQ** — fila sobre Redis, biblioteca madura no ecossistema Node.js/NestJS, suporta retry, backoff exponencial, dead-letter, prioridade e observabilidade de fila.
2. **RabbitMQ** — message broker dedicado, mais recursos de roteamento avançado, porém introduz mais uma peça de infraestrutura a operar sem necessidade clara no estágio atual.
3. **Fila baseada em banco (tabela de jobs no PostgreSQL)** — menos infraestrutura, mas menor throughput e recursos de observabilidade/retry mais rudimentares, exigindo mais código próprio.

## Decisão
Adotar **Redis + BullMQ**.

## Consequências
- Positivas: reaproveita o Redis já necessário para cache e pub/sub de WebSocket (ver [../03-architecture/scalability.md](../03-architecture/scalability.md)), reduzindo peças de infraestrutura; BullMQ fornece retry/backoff/dead-letter prontos, evitando reinventar esse mecanismo (ver regras em [../03-architecture/architecture.md](../03-architecture/architecture.md) seção 6); integração natural com NestJS.
- Negativas/trade-offs: Redis como fila não tem todas as garantias de um broker dedicado (ex.: roteamento complexo de mensagens) — aceitável, pois o produto não exige esse nível de roteamento no horizonte atual; se o volume de jobs crescer ordens de grandeza, reavaliar RabbitMQ/Kafka com um novo ADR baseado em evidência real.
- Toda fila definida segue o padrão de retry/backoff/dead-letter/idempotência descrito em [../03-architecture/architecture.md](../03-architecture/architecture.md) seção 6, sem exceção.
