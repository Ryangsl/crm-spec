# ADR-005: REST + OpenAPI como contrato frontend/backend

## Status
Aceito

## Contexto
`crm-backend` e `crm-frontend` evoluem em repositórios separados e precisam de um contrato de API versionado, claro e verificável, que outros agentes de IA também consigam consumir sem reinterpretar requisitos (ver [../05-api/api-guidelines.md](../05-api/api-guidelines.md)).

## Problema
Qual estilo de API e formato de especificação adotar para o contrato entre frontend e backend, equilibrando simplicidade, ferramentas de geração de tipos/cliente e facilidade de versionamento.

## Opções consideradas
1. **REST + OpenAPI** — endpoints por recurso, especificação declarativa em `openapi.yaml`, ecossistema maduro de geração de tipos/cliente e documentação.
2. **GraphQL** — schema único, cliente pede exatamente o que precisa; poderoso, mas adiciona complexidade (resolvers, N+1, cache diferente do HTTP tradicional) desnecessária para o estágio atual.
3. **RPC customizado (ex.: tRPC)** — forte integração de tipos ponta a ponta em TypeScript, mas acopla fortemente o cliente ao mesmo monorepo/linguagem do servidor, reduzindo a portabilidade do contrato para outros consumidores futuros (app nativo, integrações de terceiros).

## Decisão
Adotar **REST com especificação OpenAPI 3.0** como contrato oficial, versionado por prefixo de URL (`/v1`).

## Consequências
- Positivas: contrato explícito e legível por humanos e por agentes de IA sem acesso ao código-fonte de ambos os repositórios; ecossistema maduro para gerar tipos TypeScript no frontend a partir do `openapi.yaml`; portável para futuros consumidores (app nativo, integrações de parceiros) sem depender da mesma stack de linguagem.
- Negativas/trade-offs: menos flexível que GraphQL para telas que precisam de composições de dados muito variáveis — mitigado por desenhar endpoints agregados quando necessário (ex.: `/customers/{id}/interactions` já retorna histórico consolidado, ver [../05-api/openapi.yaml](../05-api/openapi.yaml)), em vez de expor granularidade excessiva.
- Exige disciplina de manter `openapi.yaml` atualizado a cada mudança de contrato (ver [../07-backend/coding-standards.md](../07-backend/coding-standards.md) seção 6).
