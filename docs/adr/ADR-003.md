# ADR-003: Monólito modular no backend

## Status
Aceito

## Contexto
O produto tem muitos módulos (CRM, Call Center, Omnichannel, Relatórios, etc. — ver [../03-architecture/architecture.md](../03-architecture/architecture.md)), mas a operação está começando pequena. É preciso decidir a granularidade de deploy/execução do backend sem comprometer a evolução futura.

## Problema
Adotar microsserviços desde o início ou um monólito, equilibrando velocidade de desenvolvimento inicial, custo operacional e capacidade de escalar módulos específicos (ex.: Call Center sob alta carga) no futuro.

## Opções consideradas
1. **Microsserviços desde o início** — um serviço por módulo (ou por domínio), com comunicação via rede/mensageria entre eles.
2. **Monólito modular** — um único processo/deploy, mas com fronteiras internas de módulo rígidas (sem acesso direto a repositório de outro módulo, comunicação preferencialmente por evento).
3. **Monólito não modular ("big ball of mud")** — um único processo sem fronteiras internas disciplinadas.

## Decisão
Adotar **monólito modular**, com possibilidade de extração futura de serviços quando houver evidência real de necessidade (ver [../07-backend/backend-architecture.md](../07-backend/backend-architecture.md) seção 10).

## Consequências
- Positivas: custo operacional e complexidade de infraestrutura mínimos no início (um deploy, uma transação de banco, debug mais simples); times pequenos/agentes de IA conseguem trabalhar em módulos diferentes sem a sobrecarga de contratos de rede entre serviços; a disciplina de módulo interno (sem acoplamento a repositório de outro módulo) preserva o caminho de extração futura.
- Negativas/trade-offs: escalar um módulo isoladamente (ex.: Call Center sob pico de chamadas) exige escalar o processo inteiro no MVP — aceitável até haver evidência de necessidade diferenciada (ver [../03-architecture/scalability.md](../03-architecture/scalability.md)); requer disciplina de code review para não deixar módulos vazarem acoplamento um para o outro (ver [../07-backend/coding-standards.md](../07-backend/coding-standards.md)).
- Rejeitada explicitamente a opção 1 (microsserviços desde o início): overengineering para o estágio atual do produto, custo de infraestrutura e operação incompatível com "evitar complexidade desnecessária antes da necessidade".
- Rejeitada a opção 3: mesmo custo operacional do monólito modular, sem nenhum dos benefícios de manutenibilidade/caminho de extração.
