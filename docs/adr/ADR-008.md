# ADR-008: Estratégia de autenticação — JWT com refresh token em cookie httpOnly

## Status
Aceito · Decisões relacionadas: [D-004](../00-governance/decision-register.md#d-004--estratégia-de-jwt), [D-005](../00-governance/decision-register.md#d-005--armazenamento-do-refresh-token), [D-006](../00-governance/decision-register.md#d-006--topologia-de-domínio-samesite-e-csrf)

## Contexto
A Fase 2 do roadmap implementa autenticação, usuários e tenants. É necessário definir de forma definitiva o tempo de vida dos tokens e onde o refresh token é armazenado no cliente, porque essa escolha determina a superfície de ataque (XSS vs. CSRF), o comportamento de logout/revogação e a complexidade do frontend.

## Problema
Como manter sessões de usuário seguras em uma API stateless multi-tenant, equilibrando risco de roubo de token, experiência de uso (não obrigar login constante) e capacidade de revogar acesso.

## Opções consideradas

**Tempo de vida do access token**
1. Curto (≈15 min) — janela de exposição pequena em caso de vazamento, exige refresh frequente.
2. Longo (horas/dias) — menos requisições de refresh, mas token roubado permanece válido por muito tempo e não há como revogar um JWT já emitido.

**Armazenamento do refresh token**
1. `localStorage`/`sessionStorage` — simples, porém legível por qualquer JavaScript: um XSS rouba a sessão de longa duração.
2. **Cookie httpOnly** — inacessível a JavaScript (mitiga XSS), mas exige atenção a CSRF quando o deploy for cross-site.
3. Apenas em memória — mais seguro, mas o usuário perde a sessão a cada reload da página, inaceitável para uso operacional diário.

## Decisão

- **Access token**: JWT, TTL de **15 minutos**, mantido apenas em memória no frontend (nunca persistido em `localStorage`).
- **Refresh token**: TTL de **7 dias**, opaco, armazenado com hash no banco, entregue ao cliente em **cookie httpOnly** com `Secure: true` em produção.
- **Rotação**: cada uso do refresh token emite um novo e invalida o anterior; reuso de um token já rotacionado é tratado como indício de comprometimento e revoga a família de tokens daquele usuário/dispositivo.
- **Revogação**: individual (logout de um dispositivo) e global (logout de todos os dispositivos).
- **`SameSite` e CSRF**: [D-006](../00-governance/decision-register.md#d-006--topologia-de-domínio-samesite-e-csrf) (`DECIDIDO`) — `SameSite=Lax`, sem `Domain` explícito (cookie host-only), `Path=/v1/auth` (o cookie nunca é enviado ao restante da API). Topologia de produção é same-site (Nginx único na frente de backend e frontend, ver [../08-devops/deployment.md](../08-devops/deployment.md) §2), o que torna `SameSite=Lax` suficiente contra CSRF sem token anti-CSRF adicional. Se a topologia migrar para cross-site no futuro, esta decisão precisa ser reaberta.
- **Reuso detectado (família de sessões)**: [D-056](../00-governance/decision-register.md#d-056--política-de-reuso-de-refresh-token-família-de-sessões) — família = todos os refresh tokens do mesmo `userId` (sem granularidade por dispositivo ainda); reuso revoga todos; resposta ao cliente é indistinguível de qualquer outro refresh token inválido (401 padrão, não vaza que houve detecção).
- **Logout global**: [D-057](../00-governance/decision-register.md#d-057--logout-global) — `POST /v1/auth/logout-all`, identifica o usuário pelo próprio refresh token apresentado (não exige access token válido), revoga toda a família.

## Consequências
- Positivas: XSS não expõe a credencial de longa duração (cookie httpOnly); janela de 15 minutos limita o dano de um access token vazado; rotação com detecção de reuso transforma roubo de refresh token em evento detectável; revogação real é possível porque o refresh token é opaco e persistido (diferente de um JWT autocontido).
- Negativas/trade-offs: o frontend precisa tratar refresh transparente (interceptor que renova em 401 e repete a requisição) e o backend precisa persistir/rotacionar tokens — complexidade aceitável frente ao ganho de segurança; cookie exige alinhamento de domínio entre frontend e API no deploy, o que restringe topologias de hospedagem (tratado em [D-006](../00-governance/decision-register.md#d-006--topologia-de-domínio-samesite-e-csrf)).
- Rejeitado `localStorage` explicitamente: incompatível com o princípio de que segurança não é sacrificada por conveniência de implementação (ver [../03-architecture/security.md](../03-architecture/security.md) seção 10).
