# ADR-008: Decisões técnicas de fundação da Fase 1 (crm-backend)

## Status
Aceito

## Contexto
A Fase 1 (fundação técnica de `crm-backend` — ver [../10-roadmap/roadmap.md](../10-roadmap/roadmap.md))
esbarrou em cinco pontos marcados `[DECISÃO PENDENTE]` em documentos anteriores que,
diferente de decisões de produto, não bloqueiam a implementação: cada um já tinha uma
recomendação registrada ou uma opção claramente mais simples/reversível. Em vez de deixar
esses pontos pendentes indefinidamente ou resolvê-los silenciosamente no código, este ADR
consolida a decisão tomada para cada um.

## Decisões

### 1. Formato de UUID: v4 (não v7)
`crm-spec/docs/04-database/database.md` seção 1 marcava v4 vs. v7 como pendente, com v7
preferível "por ordenação temporal/performance de índice". Adotado **UUID v4**
(`gen_random_uuid()` nativo do Postgres/Prisma, sem extensão adicional). Justificativa: v7
exigiria geração na aplicação ou extensão de banco não padrão, custo desnecessário no
estágio atual (poucas linhas por tabela); a paginação por cursor já usa `(created_at, id)`
como chave composta (ver [../05-api/api-guidelines.md](../05-api/api-guidelines.md) seção 4),
então a ordenação de índice por UUID não é uma dependência do contrato. Trocar para v7 no
futuro não muda o tipo de coluna nem quebra nenhum consumidor — é uma migração de baixo
risco caso o volume justifique.

### 2. Validação de DTO: `class-validator`
`crm-spec/docs/07-backend/backend-architecture.md` seção 3 já recomendava `class-validator`
"por integração nativa com NestJS pipes" como pendente-mas-recomendado. Adotado como
definitivo — nenhuma vantagem de Zod supera a integração nativa com `ValidationPipe` do
Nest para o estágio atual.

### 3. Row Level Security (RLS): adiado para a Fase 2+
`crm-spec/docs/03-architecture/security.md` seção 1.3 e `database.md` seção 5 delegavam essa
confirmação "à Fase 1/2". Decisão: **não habilitar RLS na Fase 1**. O isolamento depende
inteiramente da camada de aplicação: todo Repository lê `tenant_id` de
`TenantContextStorage` (AsyncLocalStorage, nunca de input do cliente — ver
`crm-backend/src/common/context/tenant-context.ts`), e todo endpoint tenant-scoped tem teste
automatizado de vazamento cross-tenant (ver
`crm-backend/test/e2e/tenant-isolation.e2e-spec.ts`). Justificativa: a Fase 1 só tem o grupo
"Tenancy e Acesso" (poucas tabelas, baixo volume); introduzir políticas RLS agora, antes do
modelo de dados de CRM (Fase 3) estabilizar, adicionaria complexidade sem reduzir risco real
hoje. **Revisitar obrigatoriamente antes do fim da Fase 2** (quando `CRUD de usuários` e
"auditoria básica" entram) como camada de defesa em profundidade adicional — não substitui
os testes de isolamento, que continuam obrigatórios independente de RLS.

### 4. Refresh token: entregue no corpo da resposta (não cookie httpOnly)
`security.md` seção 4 marcava como pendente "se refresh token for entregue via cookie
httpOnly". Mantido o que já estava implícito no exemplo de contrato de
`api-guidelines.md` seção 9 e no `openapi.yaml` (`refresh_token` no corpo da requisição/
resposta, `Authorization: Bearer` para o access token). Como não há cookie de sessão,
proteção CSRF clássica não se aplica. Reversível: migrar para cookie httpOnly exigiria um
ADR próprio e adicionar proteção CSRF (SameSite + token) naquele momento.

### 5. TTL de tokens
`security.md` seção 2 marcava o TTL do access token como pendente, sugerindo 15 minutos.
Adotado **900 segundos (15 min)** para o access token — já era o valor de exemplo em
`08-devops/local-development.md` seção 3 (`JWT_ACCESS_TTL=900`), agora formalizado. Refresh
token: **2.592.000 segundos (30 dias)**, sem menção anterior na documentação; escolhido como
padrão razoável para sessão "lembrada" de aplicação de uso profissional diário, configurável
via `JWT_REFRESH_TTL` sem mudança de código. Refresh tokens são de uso único (rotação: cada
`POST /v1/auth/refresh` revoga o token usado e emite um novo — ver
`crm-backend/src/modules/auth/auth.service.ts`), o que reduz o risco de um TTL longo.

## Limitação identificada durante a implementação (não é uma decisão fechada)

O contrato de login (`POST /v1/auth/login`, `api-guidelines.md` seção 9) recebe apenas
`email`+`password`, sem identificador de tenant — mas `email` é único por tenant, não
globalmente (`entities.md`, tabela `users`). `crm-backend` resolve isso buscando o usuário
por e-mail entre todos os tenants; se exatamente um usuário ativo tiver aquele e-mail, o
login prossegue normalmente. Se o e-mail existir em mais de um tenant, o login falha
(fail-closed) em vez de escolher um tenant arbitrariamente — nunca resulta em autenticar a
pessoa errada ou vazar em qual tenant o e-mail existe. Isso é aceitável para o estágio atual
porque o provisionamento de tenant é manual/assistido (`10-roadmap/mvp.md` seção 2), com
poucos tenants e baixa chance de colisão de e-mail. **Antes de permitir onboarding
self-service de tenants em volume**, este ponto precisa de uma decisão explícita (ex.:
domínio/subdomínio por tenant resolvido antes do login, ou um identificador de tenant
explícito e não-secreto no formulário de login) — registrar como novo ADR quando essa fase
se aproximar.

## Consequências
- Nenhuma decisão já aceita em ADR-001 a ADR-007 foi alterada.
- `database.md`, `security.md` e `backend-architecture.md` foram atualizados para remover os
  marcadores `[DECISÃO PENDENTE]` resolvidos aqui, apontando para este ADR.
- A limitação de resolução de tenant no login fica documentada como um risco aceito e
  monitorado, não uma decisão silenciosa.
