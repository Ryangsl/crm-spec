# ADR-004: Estratégia de multi-tenancy — banco compartilhado com tenant_id

## Status
Aceito

## Contexto
O sistema é um SaaS multi-tenant. É preciso escolher como os dados de empresas (tenants) diferentes ficam isolados uns dos outros, equilibrando segurança, custo operacional de onboarding e complexidade de infraestrutura desde o MVP (ver [../03-architecture/security.md](../03-architecture/security.md) seção 1).

## Problema
Como isolar dados entre tenants sem introduzir complexidade de infraestrutura desnecessária no estágio atual do produto (poucos tenants, operação pequena a média), mas sem inviabilizar isolamento mais forte no futuro para contas específicas.

## Opções consideradas
1. **Banco compartilhado com coluna `tenant_id`** — todas as tabelas de negócio no mesmo banco/schema, isolamento aplicado na camada de aplicação (e opcionalmente reforçado por Row Level Security).
2. **Schema por tenant** — mesmo banco físico, um schema PostgreSQL por tenant; migrations precisam rodar por schema.
3. **Banco por tenant** — instância/banco físico dedicado por tenant; isolamento mais forte, mas onboarding de tenant vira uma operação de infraestrutura.

## Decisão
Adotar **banco compartilhado com `tenant_id`** em todas as tabelas de negócio, com Row Level Security como reforço avaliado (`[DECISÃO PENDENTE]`, ver [../03-architecture/security.md](../03-architecture/security.md)).

## Consequências
- Positivas: onboarding de novo tenant é uma operação de dado (inserir uma linha), não de infraestrutura; custo de manutenção de schema único (uma migration para todos os tenants); simplicidade compatível com o estágio atual do produto.
- Negativas/trade-offs: isolamento depende de disciplina de aplicação (toda query deve aplicar `tenant_id`) — mitigado por: filtro centralizado no Repository (ver [../07-backend/backend-architecture.md](../07-backend/backend-architecture.md) seção 5), testes automatizados obrigatórios de vazamento cross-tenant (ver [../09-testing/testing-strategy.md](../09-testing/testing-strategy.md)), e avaliação de RLS como segunda camada.
- Caminho de evolução: por já existir `tenant_id` consistente em todo o modelo, migrar um tenant específico (ex.: grande conta com exigência contratual) para schema ou banco dedicado no futuro é uma operação isolada, não uma reescrita de arquitetura.
- Rejeitada schema/banco por tenant no MVP: custo operacional (migrations por schema/banco, provisionamento) incompatível com "sem criar complexidade desnecessária antes da necessidade".
